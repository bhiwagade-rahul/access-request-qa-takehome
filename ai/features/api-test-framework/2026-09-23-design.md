# API Test Framework Design

## Goal

Build a concise, deterministic TypeScript API test suite for the supplied access-request service. The suite validates behavior against the assignment specification, supports reruns against candidate builds, and produces artifacts useful for defect analysis.

## Scope and Constraints

- Use TypeScript and Jest.
- Treat `service/access-request-api.js` as an unchanged black-box service.
- Default to an already-running service at `http://localhost:4000`; allow `BASE_URL` to target another build.
- Derive data expectations from `service/data/requests.json` and the specification rather than frozen bug-specific fixtures.
- Reset server state before state-changing scenarios with `POST /__admin/reset`.
- Persist generated reports locally but do not commit them.
- The authoritative contract is `access-request-api-qa-takehome.md`; a remote build must implement that same contract.
- The local dataset is used only to derive input and expected list behavior. A remote build is supported only when it is seeded with the supplied, unmodified dataset.

## Architecture

```text
tests/
  smoke/
  functional/
  negative-boundary/
  lifecycle/
src/
  api-client.ts          Typed requests, response parsing, and error handling
  test-data.ts           Dataset loading and expected-value derivation
  assertions.ts          Reusable contracts and sorting/filter assertions
  test-setup.ts          BASE_URL validation and reset helper
reports/                 Generated, ignored artifacts
```

Tests communicate with the running service only through HTTP. `api-client.ts` centralizes URL construction and JSON handling. `test-data.ts` provides source-data-driven calculations for filter, page, and ordering assertions. Suite-local hooks reset the service before each lifecycle scenario, preventing mutation leakage.

`api-client.ts` exposes `listRequests(query)`, `getRequest(id)`, `decide(id, body)`, `bulkDecide(body)`, and `reset()`. Each method returns a typed `{ status, body }` result and preserves non-2xx JSON error bodies for error-contract assertions. `test-setup.ts` probes `GET /requests` before the suite and reports the configured URL if unreachable. Reset-dependent suites run serially (`maxWorkers: 1`) so a reset cannot race another mutation.

## Contract Matrix

| Endpoint | Success contract | Required error behavior covered |
|---|---|---|
| `GET /requests` | `200` envelope `{items,page,pageSize,total}`; defaults page 1, page size 25, requested-at descending | Invalid status/type/sortBy/sortDir/page/pageSize is `400`; page size above 100 clamps to 100 |
| `GET /requests/{id}` | `200` full record | Unknown ID is `404 {error: "NOT_FOUND", message}` |
| `POST /requests/{id}/decision` | `200` updated record; incremented version, populated decision, appended `DECIDED` history event | Invalid body/decision/version `400`; non-pending `409 ALREADY_DECIDED`; mismatched version `409 STALE_VERSION`; required blank/missing justification `422 JUSTIFICATION_REQUIRED` |
| `POST /requests/bulk-decision` | `200` ordered per-item results, with independent successes/failures | Malformed body `400`; over 100 items `400 TOO_MANY_ITEMS`; applies single-decision rules, including version check |

List tests implement all documented filters: `status` (`PENDING`, `APPROVED`, `DENIED`, `CANCELLED`), `type` (`GRANT`, `REVOKE`), `riskFlag` (exact array match), `search` (case-insensitive requester/resource/request-id substring), and sort keys `requestedAt`, `dueDate`, `requester`, `resource`, `priority`. They verify `sortDir` `asc`/`desc`, default descending direction, priority rank `LOW < NORMAL < HIGH`, and records with no due date last in both directions.

Record-contract assertions require the supplied record fields: `requestId`, `type`, `status`, `priority`, `requester`, `resource`, `requesterJustification`, `riskFlags`, `requestedAt`, `dueDate`, `version`, `decision`, and `history`. On a successful decision, assertions require version increment, `decision.outcome`, `decision.decidedBy`, `decision.decidedAt`, and `decision.justification`, plus an appended history entry whose event is `DECIDED`. The exact decision request body is `{ decision: "APPROVE" | "DENY", justification?: string, version: number }`; bulk bodies use `{ items: [{ requestId, version }], decision, justification? }`.

## Test Coverage

### Smoke

- The service is reachable and the default request-list response has the specified envelope.
- A known request can be read and has the expected record shape.

### Functional

- Valid filtering by status, type, risk flag, and case-insensitive search.
- Filtered totals and pagination metadata.
- Requested sorting, including priority rank and absent due-date placement.
- Valid approve and deny decisions update versions, decisions, and history.
- Valid bulk decision returns a per-item success result.

### Negative and Boundary

- Invalid list query values produce `400`.
- Unknown IDs produce the required `404` contract.
- Blank denial justification and risk-flagged approval without justification produce `422`.
- Invalid decision payloads produce `400`.
- Page-size clamping and bulk-size maximum behavior.

### Lifecycle

- A second decision is rejected as `ALREADY_DECIDED`.
- A stale version is rejected as `STALE_VERSION`.
- Bulk operations demonstrate independent partial success and failure.

Confirmed defects receive focused regression tests; potential defects are verified against the specification before inclusion in the report.

## Test-data Selection

`test-data.ts` has explicit selectors such as `firstPending()`, `firstPendingWithRiskFlag()`, `firstPendingWithoutRiskFlag()`, and `firstAlreadyDecided()`. Each filters the source array by the named precondition and chooses the lexicographically smallest `requestId`, which is stable when record order changes. A selector throws an error that names its precondition and the available status/risk distribution if no match exists. Lifecycle tests obtain the selected record’s original version from the same source file; they never assume a fixed ID or version.

The stale-version flow is: reset; read a selected pending record; submit a decision with a deliberately mismatched version while it is still pending; assert `409 STALE_VERSION` and that the record remains unchanged. The already-decided flow is: reset; decide a pending record; read its updated version; submit again with that current version; assert `409 ALREADY_DECIDED`. This avoids relying on unspecified precedence when both status and version are invalid.

The partial-bulk flow is: reset; pre-decide one pending record and read its updated version; select a distinct pending record and use its source version; bulk-submit both records using their current versions. Assert the pre-decided item is `FAILED` with reason `ALREADY_DECIDED`, the pending item is `SUCCESS`, then read both records to verify state. A separate bulk stale-version case uses an otherwise pending item with a deliberately mismatched version, asserting `FAILED` with reason `STALE_VERSION`.

## Determinism and Flakiness

Tests do not depend on execution order. Stateful scenarios reset data before setup; each test uses the deterministic selectors above. Jest runs serially because the externally running service has a single shared in-memory state. The suite fails fast when `BASE_URL` is unreachable. There are no arbitrary sleeps: requests wait only for their HTTP response.

## Reporting

Generated artifacts are stored under `reports/`:

```text
reports/latest/{junit.xml,results.json,run-metadata.json}
reports/runs/<UTC-timestamp>/{junit.xml,results.json,run-metadata.json}
```

`results.json` records a schema version, run summary, timestamp, environment metadata, and one entry per test (`name`, `layer`, `status`, `durationMs`, and sanitized failure evidence). `run-metadata.json` records timestamp, `BASE_URL`, Node version, and Git revision; the revision is `null` when unavailable. `junit.xml` is produced by the Jest reporter for CI-compatible consumers. `latest/` is overwritten every run; the timestamped run directory is retained locally. Failure evidence is sanitized and limited to what supports diagnosis. `reports/` is ignored by Git.

## README and Defect Report

The README will document the manually started service workflow, configuration, layered strategy, reset trade-off, flakiness policy, ten-minute regression selection, and one-day expansion ideas. The defect report will contain only verified specification deviations, with severity rationale, minimal repro, expected versus actual behavior, root-cause hypothesis, and suggested fix. Unspecified behavior will be listed separately as spec-gap observations.
